# Сортировка каталога (рейтинг, дата публикации) — Design Document

Дата: 2026-10-04
Статус: Approved

## 1. Обзор

Каталог (`/api/search`) сейчас всегда сортирует результаты по релевантности (при непустом запросе) или по количеству скачиваний (при пустом). Пользователь не может отсортировать выдачу по рейтингу или по дате публикации последней версии. Добавляем выбор сортировки с переключением направления. Сортировка применяется к уже отфильтрованному набору (тип, категория, поиск) — то есть работает «в рамках выбранного типа» автоматически.

**Ключевые решения:**

| Решение | Выбор |
|---|---|
| Реализация | Динамический ORDER BY в нативном SQL (`SearchAdapter`), без миграций схемы |
| Варианты сортировки | `relevance` / `downloads` (текущее поведение), `rating`, `published` |
| Направление | `asc` / `desc` для каждого варианта |
| Сортировка vs поиск | Выбор пользователя приоритетнее; по умолчанию (не выбрано) — релевантность/скачивания как сейчас |
| Отклонено | Денормализация (`avg_rating`, `published_at` в `elements`) — требует миграции и синхронизации; сортировка на фронте — ломает пагинацию |

## 2. Бэкенд

### 2.1. API

`GET /api/search` — новые опциональные параметры:

- `sort`: `relevance` (по умолчанию) | `downloads` | `rating` | `published`
- `order`: `desc` (по умолчанию) | `asc`

Некорректные значения → 400 Bad Request (то же поведение, что у других невалидных параметров REST-слоя).

### 2.2. Изменения по слоям

- `SearchQuery` (application/dto) — новые поля `sort`, `order` (типизированные enum'ы `SortBy`, `SortOrder` в application/dto).
- `SearchController` — принимает `sort`/`order` как строки, валидирует (недопустимое значение → 400), передаёт в `SearchUseCase.search(...)`.
- `SearchUseCase` — прокидывает параметры в `SearchQuery`.
- `SearchAdapter.search()` — ORDER BY выбирается из фиксированного набора готовых SQL-фрагментов (никакой интерполяции пользовательского ввода):
  - `rating`: `LEFT JOIN LATERAL (SELECT AVG(r.rating) AS avg_rating FROM ratings r WHERE r.element_id = e.id) r ON true` + `ORDER BY r.avg_rating <direction> NULLS LAST`; элементы без оценок — в конце независимо от направления.
  - `published`: подзапрос `(SELECT MAX(v.published_at) FROM element_versions v WHERE v.element_id = e.id AND v.status = 'PUBLISHED')` + `ORDER BY ... <direction> NULLS LAST`; без опубликованных версий — в конце.
  - `relevance`/`downloads`: текущий ORDER BY без изменений.
  - Стабилизирующий вторичный ключ сортировки для всех вариантов: `e.id` (детерминированный порядок страниц).

## 3. Фронтенд

- `ui/src/api/search.ts` — параметры `sort`, `order` в запросе.
- `ui/src/pages/CatalogPage.tsx`:
  - Рядом с чипами типов/категорий — блок «Сортировка»: `ToggleButtonGroup` (Популярность / Рейтинг / Дата публикации) + `ToggleButton`-иконка со стрелкой (вверх/вниз) для смены направления.
  - Состояние `sort` (`'relevance' | 'rating' | 'published'`, по умолчанию `'relevance'`) и `order` (`'desc' | 'asc'`, по умолчанию `'desc'`).
  - Ключ react-query включает `sort` и `order`.
  - «Популярность» скрывает переключатель направления (там всегда desc, направление не имеет смысла).

## 4. Ошибки

| Ситуация | Ответ |
|---|---|
| Неверное значение `sort`/`order` | 400 Bad Request |
| Элементы без рейтинга / без опубликованных версий | В конце списка (`NULLS LAST`) |

## 5. Тесты

- `SearchAdapterTest` (или интеграционный тест на H2/Testcontainers, следуя существующим паттернам) — сортировка по `rating` (элементы без оценок в конце, asc/desc), по `published` (берётся `MAX(published_at)` только среди `PUBLISHED`-версий, drafts не влияют), по умолчанию — прежнее поведение; сортировка в рамках выбранного `type`.
- Тест `SearchController` — 400 при недопустимом `sort`/`order`; параметры прокидываются.
- `CatalogPage.test.tsx` — выбор варианта сортировки меняет параметры запроса; переключение направления; «Популярность» без стрелки направления.

## 6. Не делаем

- Миграции схемы и денормализованные колонки рейтинга/даты.
- Сортировка на клиенте.
- Сортировка по другим полям (имя, размер и т.п.).
