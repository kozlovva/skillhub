# Дизайн: визард публикации элемента (2 шага)

Дата: 2026-10-04

## Контекст

Сейчас `UploadPage` требует заполнить название, описание, тип и т.д. руками, хотя загружаемый zip-архив обязан содержать `manifest.json` с обязательными полями `name` и `version` (проверка на сервере в `ArchiveService`) и опциональными `description` и `type`. Данные дублируются: пользователь вводит то, что уже есть в архиве.

Решение: перевернуть флоу — сначала файл, потом метаданные, с предзаполнением формы из манифеста. Выбран вариант B: визард из двух шагов на MUI Stepper. Бэкенд не меняется.

## Архитектура

Только фронтенд (`ui/`). `UploadPage` переписывается в визард:

- MUI `Stepper`, linear, шаги не кликабельны вперёд (только «Назад»).
- Оба шага — состояния одной страницы (не отдельные роуты); файл хранится в памяти как `File`, переходы ничего не теряют.
- Публикация — существующая логика: `create` (если элемент ещё не создан, отслеживается через `createdRef`) + `publishVersion(slug, file, changelog)`.

## Шаг 1 — Архив

- Dropzone: drag&drop + клик для выбора файла (как сейчас).
- После выбора файла манифест парсится в браузере библиотекой `fflate` (минимальная зависимость, без серверного участия).
- Из zip читаются: `manifest.json` (JSON) и список записей (имена, размеры).
- Валидация, зеркалит серверные правила:
  - `manifest.json` существует в корне архива;
  - это валидный JSON;
  - поля `name` и `version` присутствуют;
  - `version` — semver.
- Результат показывается карточкой: имя, версия, тип, описание из манифеста + количество файлов и суммарный размер архива.
- Любая ошибка валидации — инлайн-сообщение на шаге 1, переход на шаг 2 заблокирован (кнопка «Далее» неактивна). Пользователь выбирает другой файл и повторяет.

## Шаг 2 — Метаданные

Форма, предзаполненная из манифеста:

| Поле формы | Источник |
|---|---|
| Название | `manifest.name` |
| Описание | `manifest.description` (может отсутствовать) |
| Тип | `manifest.type` (если нет — пусто; поле обязательное) |
| Slug | автогенерация из `manifest.name` (slugify), редактируемое |

Ручные поля (не из манифеста): команда, видимость, категория, теги, changelog.

Сбоку — read-only список содержимого архива (имя + размер из записей zip). Существующий компонент `FileTree` не используется: он завязан на серверные `FileDto` и `onOpenFile`.

Кнопка «Назад» возвращает на шаг 1. При замене файла на шаге 1 предзаполнение из нового манифеста перезаписывает только те поля, которые пользователь не правил руками.

## Ошибки

- Шаг 1: битый zip / нет `manifest.json` / нет `name` или `version` / не-semver — инлайн на шаге 1.
- Шаг 2, публикация: ошибки `create`/`publishVersion` — как сейчас (снекбар через `toApiError`), 409 на slug — инлайн-ошибка поля slug, состояние «элемент уже создан» сохраняется (`createdRef`), повторный сабмит продолжит с публикации версии.

## Тестирование (Vitest)

- Парсинг манифеста из zip: валидный, битый JSON, нет манифеста, нет `name`/`version`, не-semver.
- Подстановка полей формы и автогенерация slug из name.
- Блокировка перехода на шаг 2 при невалидном архиве.
- Замена файла на шаге 1: перезапись только нередактированных полей.
- Сабмит на шаге 2: вызовы `create` + `publishVersion`, 409 на slug.

## Вне объёма

- Изменения бэкенда, новых эндпоинтов нет.
- Переиспользование `FileTree` для превью архива.
